# Cyber Incident Explorer v0.5.40

架空の企業システム構成図を見ながら、サイバー攻撃の進行、対策の作用点、効果の限界を学ぶ日本語のWeb教材です。

## 学習の進め方

1. シナリオを選び、対策をOFFにして攻撃を最後まで実行します。
2. 完了後の「対策を変えて比較」を押し、対策を選んで再実行します。
3. 前回と今回の結果を比べ、「解説」で作用範囲と限界を確認します。

## v0.5.37の変更（08：URL取得機能のGET悪用も情報流出経路に追加）

- **シナリオの前提を明示：** 正規利用者が公開レポートのURLを指定して要約を依頼し、AI業務アプリが許可済みURLへHTTPS GETで取得します。外部文書の本文は攻撃者が改ざん可能な**未信頼データ**ですが、取得自体は正規処理です。
- **攻撃経路を選択可能に：** 08の「今回の外部流出経路」で **GET（URL取得ツールの悪用）／POST（外部送信ツールの悪用）** を切り替えて比較できます。GET経路では、Agentが取得済み機密情報をクエリパラメータに含めた攻撃者宛てURLへのアクセスを要求する想定です。実際のネットワーク通信は発生しません。
- **技術対策の作用範囲：** ①文書APIの最小権限（STEP 04）、②**タスク単位のツール／URL制御**（STEP 05：正規のGETは許可、攻撃者宛てGETと不正なPOSTを実行前に拒否）、③**GET／POST双方に適用する出口宛先制御**（STEP 05）。対策は3つのまま、効果のない監視スイッチは追加していません。
- **重要な限界：** ドメインの許可リストだけでは、許可済みドメインへのクエリ・送信内容による漏えいを必ず防げません。URLのホスト・パス・クエリ・リダイレクト先・解決された宛先、ツール引数、タスクとの整合を評価する必要があります。
- **図の連動：** 青点線＝正規の要約依頼、橙点線＝公開URL取得で戻った未信頼文書本文、赤＝Agentによる不正なAPI・GET／POST操作、緑×＝防御地点。STEP 05では選択したGET／POSTを明示します。
- **履歴：** 後段の送信を拒否してもSTEP 04で成立した機密文書の読取は消しません。既存9シナリオを変更せず、08の比較・全初期化も維持。
- [OWASP：AI Agent Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html) ／ [OWASP：LLM Prompt Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) ／ [OWASP：SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)。

**固定条件：** 正規の公開URLと攻撃者の受信先は別ホスト。攻撃者は外部文書の本文を改ざんでき、Agentは指示を誤採用し、GET・POSTの外部要求は制御OFFの場合に成立します。対策ONでは今回のタスク外URL・引数・未承認送信先を確実に拒否すると仮定します。実製品の検知率やあらゆる漏えいの阻止を保証するものではありません。

## v0.5.35の変更（08 AIアプリへの攻撃）

- 08「AIアプリへの攻撃」を実装。**計10シナリオ**から選べます。既存9件の画面と操作方法は維持しています。
- **攻撃の6ステップ：** ①正規利用者が公開文書の要約を依頼 → ②AIアプリが悪意ある指示を含む外部文書を取得 → ③AIが文書本文の指示を権限ある命令と誤認 → ④社内機密文書APIの閲覧を試行 → ⑤ツールを使って不正な宛先への外部POSTを試行 → ⑥送信成立または阻止。
- **技術対策は3件のみを切り替え対象とする：**
  1. **社内文書APIの最小権限**：STEP 04で、本来不要な機密文書の閲覧をバックエンド認可で拒否。
  2. **外部送信ツールの実行権限**：STEP 05で、要約タスクに許可されていない任意宛先POSTツールを実行前に拒否。
  3. **出口通信の宛先許可制御**：STEP 05で、許可外の攻撃者ドメインへの通信をProxy／FWで拒否。
- 正規の要約依頼は青点線、攻撃・不正ツール操作は赤線、阻止地点は緑×、未到達の後続操作は灰線で表現します。
- **過去の事実を消さない：** 読取後に送信を止めても、AIが機密文書を参照した履歴は残ります。
- モデルへの注意喚起、一般的なプロンプトフィルタ、ログ通知だけで必ず防げるという設定にはせず、モデルとは独立した **API・ツール・ネットワークの強制的認可** を比較します。
- **固定条件：** 教材上、外部文書の命令をAIが誤採用したと仮定。各防御スイッチは今回の操作と通信先に作用するポリシーが正しく設定されている場合です。実際のAIモデル、社内API、外部通信は呼び出しません。

## v0.5.34の変更（07 内部不正／情報持ち出し）

- **07「内部不正／情報持ち出し」** を実装。学習可能なシナリオは **9件** になりました。従来の8件と操作体系を維持しています。
- **攻撃の6ステップ：** 正規の従業員IDでログイン → 業務不要な機密フォルダを参照 → 機密ファイルを会社管理PCに保存 → 同じPCの保存領域で持ち出し準備 → SWG／CASB・DLPを経由して未許可の個人クラウドへアップロード → 外部の個人クラウドが機密情報を受信。
- **有効なIT対策4件のみ切り替え対象：**
  1. 機密フォルダの最小権限（RBAC／ACL）：STEP 02で業務上不要なファイル閲覧を拒否
  2. 管理端末への機密ファイル保存制限：STEP 03で保存を拒否（既に成立した閲覧履歴は残る）
  3. 未許可クラウドのアップロード制限（SWG／CASB）：STEP 05で個人用クラウドへの送信を拒否
  4. 機密情報DLP：STEP 05でSWG通過後の検査可能な機密ファイル送信を拒否
- **認証は成功したまま**、認可・端末への複製・出口制御を別々に評価。MFA・一般的なログ監視・SIEM通知だけでこの正規ユーザーの悪意を止めた扱いにはしません。
- 機器と処理を区別：IdP、機密File Server、従業員PC、同じPC内の保存領域（別PCではない）、SWG／CASB、DLP、個人クラウド、SIEM。通過済みの赤経路と、緑の阻止地点・未到達区間を連動。
- **固定条件：** 管理PCからの送信が必ずSWG／CASB・DLPの検査経路を通り、機密ファイルは分類済みで検査可能。対象外経路・暗号化ZIP・画像撮影・個人端末・正規の閲覧権限による悪用には別途対策が必要です。
- 08「AIアプリへの攻撃」は引き続き準備中です。検証詳細は [QA-REPORT.md](QA-REPORT.md)。

## v0.5.33の変更（06 BECをITセキュリティ中心に再設計）

- 06「ビジネスメール詐欺（BEC）」を、**業務上の口座確認・承認の切り替え主体から、IT防御の作用点を学ぶシナリオ**へ変更しました。旧版の業務統制3スイッチは撤去。
- **攻撃の6ステップ：** ①取引先のパスワード窃取 → ②非準拠端末からIdP認証を試行 → ③メールボックスの請求情報を不正閲覧 → ④不審な受信ルールを作成 → ⑤正規メールアカウントから不正な口座変更メール送信 → ⑥受信側の経理が独立確認を省略した場合に誤送金。
- **IT対策の4スイッチ：**
  1. フィッシング耐性MFA（STEP 02：盗用パスワードだけではログインできない）
  2. 準拠端末の条件付きアクセス（STEP 02：今回の未管理端末を拒否）
  3. 不審メールルール検知と**セッション自動失効・アカウント停止**（STEP 04：作成済みルールは残るが、後続送信を止める）
  4. 不正送信メールの**自動保留**（STEP 05：今回のリスク・内容ルールに一致したメールだけを配送前に保留）
- 取引先IdP、メールボックス、不審ルール操作、送信メール保護、受信側経理の違いを構成図で示します。過去に起きた不正アクセスや情報閲覧を、後の対策ONによって取り消すことはありません。
- 折り返し確認・独立承認・送金前照合は**対策切り替え欄ではなく解説の補完策**として扱います。ITだけで金銭被害を必ず阻止できるとは説明しません。
- 現行の他7シナリオと全体のUI構成を維持。ローカルQA結果は [QA-REPORT.md](QA-REPORT.md) を参照。

**教材の固定条件：** 攻撃者はパスワードのみ窃取し、認証済みセッションや準拠端末は持ちません。自動封じ込め・送信保護は、今回の不審操作・不正メールにルールが一致し自動遮断まで成功する条件です。単なる監視ON、一般的なメールフィルタの導入だけで防御できる意味ではありません。

**参考資料**
- [CISA：フィッシング耐性MFA](https://www.cisa.gov/sites/default/files/2023-01/fact-sheet-implementing-phishing-resistant-mfa-508c.pdf)
- [Microsoft：侵害されたメールアカウントへの対応](https://learn.microsoft.com/en-us/defender-office-365/responding-to-a-compromised-email-account)
- [Microsoft：不審な受信ルールの調査](https://learn.microsoft.com/en-us/defender-xdr/alert-grading-playbook-inbox-manipulation-rules)

## v0.5.32の変更（06 ビジネスメール詐欺：BEC）

- 06「ビジネスメール詐欺」を追加し、学習可能なシナリオを**合計8件**にしました。既存7件の画面・操作方法は維持しています。
- **想定：** 取引先の正規メールアカウントがすでに侵害されており、実在の請求・支払情報と本物の返信スレッドを使って不正な振込先変更を求めます。送信元認証の成功だけでは、支払先変更の正当性を保証できません。
- **攻撃の6ステップ：** 取引先メール侵害 → 請求情報把握 → 不正な口座変更メール → 経理担当の確認 → 振込先台帳の変更 → 誤送金。
- **防止効果のある3対策のみ切替対象：** ①事前登録番号での折返し確認（STEP 04）、②取引先との独立した根拠による振込先変更承認（STEP 05）、③改ざん後の台帳と独立した正規口座情報による送金直前の照合（STEP 06）。複数ONでは最も早い阻止地点で止まります。
- 正当な確認電話は**青線**、詐欺の進行は**赤線**、阻止点は**緑×**、後続未到達は**灰線**で表示。架空の相手・社内担当者・支払先台帳・金融機関と不正受取口座を区別しました。
- SPF／DKIM／DMARC、自社MFA、一般的なメール注意喚起は「今回の被害を確実に阻止するスイッチ」に含めず、解説で作用範囲と限界を説明します。
- 06の設計根拠：[FBI IC3 BEC](https://www.ic3.gov/CrimeInfo/BEC)、[MITRE ATT&CK T1657 Financial Theft](https://attack.mitre.org/techniques/T1657/)。
- 07「内部不正／情報持出し」と08「AIアプリへの攻撃」は引き続き準備中です。検証内容は [QA-REPORT.md](QA-REPORT.md) を参照してください。

**留意点：** 対策ONによる阻止結果は、取引先が確認電話で真偽を否定できること、承認者が改ざんされていない独立情報を持つこと、送金前照合でも独立した情報が利用できることを仮定した教育用モデルです。実製品・組織の防御を保証しません。

## v0.5.31の変更（DDoS正常通信の接続経路）

- CASE 05の一般利用者の青い通信経路を、必ず **「一般利用者 → 上流DDoS対策 → 企業接続回線 → 公開Webサービス」** の順に修正しました。一般利用者が上流DDoS対策を飛ばして企業回線へ直接接続したように見える経路は廃止。
- 上流DDoS対策への入口、上流から企業接続回線への出口、企業回線から公開Webへの通信を別々の矢印で表示します。青い矢印は実際の機器の境界を指し、攻撃の赤線とは混同しない構成です。
- 対策ONでは青実線で正常通信が公開Webまで通過。対策OFFでも設置点を通る通信の経路は同じですが、緩和されない攻撃で企業回線が飽和するため、青点線は企業回線までで停止・遅延を示します。
- 「通常構成」の灰色の論理接続と、STEP 04の学習解説にも同じ接続順序を反映しました。
- ブラウザで対策OFF／ONの6ステップ、正常経路3区間、既存6シナリオの各バリエーションを回帰検証しました。詳細は [QA-REPORT.md](QA-REPORT.md) を参照。

## v0.5.30の変更（05 DDoS表示のタイミングと矢印）

- **対策OFF：** STEP 03（企業回線の飽和が確定する段階）で「公開Webサービス」を赤色へ変更。「回線飽和・アクセス困難」と表示します。STEP 05まで赤色化を遅らせません。

## v0.5.29の変更（DDoS教材の簡素化・正常通信の可視化）

- CASE 05の対策切り替えを **「上流DDoS対策（攻撃通信の除去・分散）」の1件** に一本化しました。
