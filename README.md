# Cyber Incident Explorer v0.5.32

架空の企業システム構成図を見ながら、サイバー攻撃の進行、対策の作用点、効果の限界を学ぶ日本語のWeb教材です。

**公開サイト:** [Cyber Incident Explorer](https://peridotan.github.io/cyber-incident-explorer/)  
**ソースZIP:** [cyber-incident-explorer-v0.5.32.zip](https://peridotan.github.io/cyber-incident-explorer/cyber-incident-explorer-v0.5.32.zip)

## 収録シナリオ

- ランサムウェア（リモートアクセス経由）
- ランサムウェア（悪性メール添付経由）
- フィッシングからのSaaS侵害
- サプライチェーン攻撃（委託先・保守接続経由）
- サプライチェーン攻撃（正規ソフトウェア更新経由）
- 公開WebアプリケーションへのSQLインジェクション
- **DDoS／サービス停止（05）**
- **ビジネスメール詐欺（06、新規）**

## 学習の進め方

1. シナリオを選び、対策をOFFにして攻撃を最後まで実行します。
2. 完了後の「対策を変えて比較」を押し、対策を選んで再実行します。
3. 前回と今回の結果を比べ、「解説」で作用範囲と限界を確認します。

## v0.5.32の変更（06 ビジネスメール詐欺：BEC）

- 06「ビジネスメール詐欺」を追加し、学習可能なシナリオを**合計8件**にしました。既存7件の画面・操作方法は維持しています。
- **想定：** 取引先の正規メールアカウントがすでに侵害されており、実在の請求・支払情報と本物の返信スレッドを使って不正な振込先変更を求めます。送信元認証の成功だけでは、支払先変更の正当性を保証できません。
- **攻撃の6ステップ：** 取引先メール侵害 → 請求情報把握 → 不正な口座変更メール → 経理担当の確認 → 振込先台帳の変更 → 誤送金。
- **防止効果のある3対策のみ切替対象：** ①事前登録番号での折返し確認（STEP 04）、②取引先との独立した根拠による振込先変更承認（STEP 05）、③改ざん後の台帳と独立した正規口座情報による送金直前の照合（STEP 06）。複数ONでは最も早い阻止地点で止まります。
- 正当な確認電話は**青線**、詐欺の進行は**赤線**、阻止点は**緑×**、後続未到達は**灰線**で表示。架空の相手・社内担当者・支払先台帳・金融機関と不正受取口座を区別しました。
- SPF／DKIM／DMARC、自社MFA、一般的なメール注意喚起は「今回の被害を確実に阻止するスイッチ」に含めず、解説で作用範囲と限界を説明します。
- 06の設計根拠：[FBI IC3 BEC](https://www.ic3.gov/CrimeInfo/BEC)、[MITRE ATT&CK T1657 Financial Theft](https://attack.mitre.org/techniques/T1657/)。
- 07「内部不正／情報持出し」と08「AIアプリへの攻撃」は引き続き準備中です。検証内容は [QA-REPORT.md](QA-REPORT.md) を参照してください。

**留意点：** 対策ONによる阻止結果は、取引先が確認電話で真偽を否定できること、承認者が改ざんされていない独立情報を持つこと、送金前照合でも独立した情報が利用できることを仮定した教育用モデルです。実製品・組織の防御を保証しません。

## v0.5.31の変更（DDoS正常通信の接続経路）

- CASE 05の一般利用者の青い通信経路を、必ず **「一般利用者 → 上流DDoS対策 → 企業接続回線 → 公開Webサービス」** の順に修正しました。一般利用者が上流DDoS対策を飛ばして企業回線へ直接接続したように見える経路は廃止。
- 上流DDoS対策への入口、上流から企業接続回線への出口、企業回線から公開Webへの通信を別々の矢印で表示します。青い矢印は実際の機器の境界を指し、攻撃の赤線とは混同しない構成です。
- 対策ONでは青実線で正常通信が公開Webまで通過。対策OFFでも設置点を通る通信の経路は同じですが、緩和されない攻撃で企業回線が飽和するため、青点線は企業回線までで停止・遅延を示します。
- 「通常構成」の灰色の論理接続と、STEP 04の学習解説にも同じ接続順序を反映しました。
- ブラウザで対策OFF／ONの6ステップ、正常経路3区間、既存6シナリオの各バリエーションを回帰検証しました。詳細は [QA-REPORT.md](QA-REPORT.md) を参照。

## v0.5.30の変更（05 DDoS表示のタイミングと矢印）

- **対策OFF：** STEP 03（企業回線の飽和が確定する段階）で「公開Webサービス」を赤色へ変更。「回線飽和・アクセス困難」と表示します。STEP 05まで赤色化を遅らせません。
- **対策ON：** 回線の保護をSTEP 03で確認し、STEP 04で正常通信が到達したら公開Webを緑色へ。STEP 05で「正常アクセス可能」と表示します。
- 赤い公開Webは **可用性への影響** を示します。Webサーバー自体の侵害を意味しません。
- DDoSの青い正常通信の矢印は、SVGマーカーを固定サイズ（`markerUnits="userSpaceOnUse"`、9×8）に変更。線の太さによる不自然な拡大を防ぎ、Webコンポーネントの縁との間隔も調整しました。
- 下部結果表示と解説のタイミングを合わせ、攻撃の赤線・遮断の緑×・正常利用者の青線の意味を維持しています。
- 既存6シナリオ、全初期化、対策比較の回帰確認を実施しました。詳細は [QA-REPORT.md](QA-REPORT.md) を参照してください。

## v0.5.29の変更（DDoS教材の簡素化・正常通信の可視化）

- CASE 05の対策切り替えを **「上流DDoS対策（攻撃通信の除去・分散）」の1件** に一本化しました。
- WAF・アプリ側レート制限・可用性監視は、今回のL3/L4回線飽和を防ぐ切り替え対策から外し、解説に作用範囲と限界を記載しました。
- 洗浄（悪性通信を識別・除去）、CDN（エッジ配信・処理）、Anycast（経路・拠点の分散）の違いを明確にし、単にCDN／Anycastを導入すればDDoSが防げるという誤解を避けました。
- 防御ONでは、**青実線**で「一般利用者→保護経路→企業接続回線→公開Webサービス」の正常アクセスを表示し、Webを「正常アクセス可能」と判定します。
- 防御OFFでは、**青点線**で正常通信の遅延と回線飽和を表示します。攻撃経路（赤）、遮断（緑×）、正常通信（青）を区別します。
- ON/OFF比較、全初期化、攻撃履歴の保持、既存6シナリオの回帰テストを実施しました。詳細は [QA-REPORT.md](QA-REPORT.md) を参照してください。

**学習上の前提：** ONで守れるのは今回の固定条件（攻撃量が緩和容量内、保護経路・オリジン側の構成が適切、Web自体は正常）での例です。すべての環境での防御を保証するものではありません。

## v0.5.28の変更

- 05「DDoS／サービス停止」を追加（学習シナリオ計7件）。L3/L4の大量通信による企業回線飽和と、正常利用者のサービス利用不能を6ステップで可視化。
- 上流のトラフィック洗浄、CDN／Anycast、WAF、アプリ側のレート制限、可用性監視の5対策を比較可能にしました。
- 上流の対策は今回の攻撃量・契約容量・経路の条件を満たす場合に限り阻止とし、WAF／レート制限／監視のみでは上流の回線飽和を阻止できないことを明示。
- 攻撃通信と正常利用者通信を区別し、阻止後の未到達経路は通過済みの赤線にしないようにしました。
- 公開サイトのHTMLソースを `index.html` として管理し、GitHub Actionsで配布用ZIPを組み立てる方式に変更（従来のv0.5.27のZIP.b64は履歴保持用に残します）。
- 06 BEC、07 内部不正／情報持ち出し、08 AIアプリへの攻撃は引き続き次期候補です。

**注記：** 本教材のDDoS防御結果は架空の固定条件で決まります。現実の攻撃量、ルーティング、対策サービスの容量・構成によって効果は異なり、個別製品の防御を保証しません。

## 重要な前提

本教材は条件を固定した教育用の決定論的シミュレーションです。実際の不正アクセス、マルウェア実行、外部通信は行いません。画面上の検知・阻止結果は、実製品の検知率や実環境での効果を保証するものではありません。
